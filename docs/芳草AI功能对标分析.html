采集引擎架构
任务队列·进度追踪·失败重试		 串行采集，阻塞 API 进程；在 main.py lifespan 中直接运行；无独立 Worker 需重构 【优化】按 design-v2 拆为独立 Worker 进程；API 只负责任务编排；增加任务进度、失败重试、成本统计、批次管理
内容分发机制
自动发布·多平台·状态追踪		 distribution 仅手动记录发布 URL，无自动发布能力，无平台适配器 需升级 【优化】增加 DistributionProvider 适配接口；支持"一键发布引导+人工确认"半自动模式；发布 URL 作为归因主键
GEO/AEO 分析精度

竞品分析

关键风险与冲突 — 实施前必须决策

芳草文档的通用运营能力与 GEO design-v2 的医生垂直方向存在边界冲突
⚠ 产品定位冲突
design-v2 明确"聚焦医生个人品牌，暂不支持通用企业品牌监测"。芳草文档覆盖实体门店/工厂/电商/专业服务/个人IP等全行业。
需决策：是在医生场景下做垂直化适配（推荐），还是扩展为通用平台（与 design-v2 冲突）？
⚠ 医疗合规约束
芳草的"自动发布""自动获客""AI客服"在医疗场景下受严格监管。design-v2 要求"无人审核不自动发布医疗内容"。
需决策：所有自动动作必须增加人工审核门禁；AI客服需明确"非诊疗建议"免责声明。
⚠ 外部平台依赖
矩阵发布/AI引流/私域经营依赖抖音/小红书/微信等平台API。这些平台API开放度有限、合规风险高、成本不可控。
建议：采用"人工确认通道优先，自动化逐步接入"策略；不承诺全平台自动发布。
⚠ 架构复杂度控制
芳草功能矩阵庞大（20+模块），若全部纳入会显著超出 design-v2 的"模块化单体+Worker"边界。
建议：严格按 P0→P3 优先级推进；每阶段独立验收；不引入微服务/Kafka/K8s；视频/混剪等重模块作为可选插件而非核心依赖。
