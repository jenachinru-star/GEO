# 总体设计方案

## 1. 产品定义

### 1.1 一句话定义

帮助医生和其授权团队了解医生在 AI 回答与 AI 搜索中的真实可见度，识别缺失的权威信息与内容机会，生成有证据、可审核、可追踪的医疗内容，并持续验证发布后的可见度变化。

### 1.2 核心用户

- 医生本人：维护真实资料、查看可见度、审核内容。
- 医生运营人员：管理问题、生成草稿、登记发布、跟踪效果。
- 医院或机构管理员：未来管理多个医生与成员权限。
- 平台运营/合规人员：处理平台配置、异常、审计和合规规则。

### 1.3 核心价值闭环

资料可信化 → 问题体系化 → 多平台监测 → 证据化分析 → 内容机会识别 → 合规内容生产 → 发布追踪 → 再监测 → 效果归因。

系统不应只输出一个百分比，而应回答五个业务问题：

1. 哪些用户问题中，AI 根本没有提到医生？
2. 提到医生时，是中性描述、明确推荐，还是负面/风险性内容？
3. AI 引用了哪些来源，来源是否属于医生可控制的权威页面？
4. 哪些竞品医生或第三方页面获得了更多推荐和引用？
5. 发布哪类内容后，哪些问题和来源发生了可验证变化？

## 2. 产品范围

### 2.1 V2 必须支持

- IAM 登录与可靠会话；
- Workspace 数据隔离和基础成员角色；
- 医生资料、别名、执业机构、专业方向和公开证据来源管理；
- 语义问题分类、版本和启停；
- 普通模型与联网搜索两类采集；
- 采集任务进度、失败、重试、成本和历史批次；
- 提及、推荐、排名、引用、竞品和来源分析；
- 原始回答与分析证据回溯；
- 内容机会、草稿、事实检查、审核、发布和归因；
- 合规门禁、审计日志和基础通知；
- Dashboard、监测数据中心、语义库、内容中心和个人资料。

### 2.2 V2 暂不支持

- 面向任意企业品牌的通用监测；
- 自动登录并大规模抓取消费者 AI 网页端；
- 无人审核自动发布医疗内容；
- 患者病例、诊断记录或问诊数据管理；
- 复杂医院 HIS/EMR 集成；
- 微服务、跨地域多活和复杂数据湖；
- 依赖向量数据库的大规模通用知识问答；
- 完整支付结算，仅保留可配置的配额和套餐接口边界。

## 3. 总体架构

### 3.1 逻辑架构

    Web 前端
      ├─ 身份与 Workspace
      ├─ 医生资料
      ├─ 语义问题
      ├─ 监测任务与结果
      ├─ 内容中心与审核
      └─ 发布与效果
            │
            ▼
    FastAPI 模块化单体
      ├─ Auth / Workspace
      ├─ Doctor / Evidence
      ├─ Semantic / Prompt
      ├─ Monitoring / Analysis
      ├─ Content / Compliance
      ├─ Distribution / Attribution
      └─ Admin / Audit
            │
      ┌─────┴──────────┐
      ▼                ▼
    PostgreSQL       采集 Worker
                       ├─ 普通模型适配器
                       ├─ 联网搜索适配器
                       └─ 外部工具适配器

### 3.2 部署边界

初期部署三个进程即可：

1. frontend：静态资源或 Vite 构建产物；
2. api：FastAPI，只负责短请求和任务编排；
3. worker：从数据库领取采集、分析、生成和发布任务。

API 进程不得执行持续数分钟的全量采集。定时任务不得随每个 Web Worker 重复启动。

### 3.3 为什么不用微服务

当前业务量和团队规模不足以抵消微服务带来的部署、调用、日志、事务和版本协调成本。模块化单体可以先建立清晰边界，未来只有当独立模块出现显著不同的扩缩容或安全边界时再拆分。

## 4. 领域模块

### 4.1 Identity 模块

负责 IAM 登录、会话、用户状态、Workspace 成员和角色。业务接口不能直接信任 JWT 中的 user_id，而应通过当前会话解析 User 和 WorkspaceContext。

### 4.2 Doctor 模块

负责医生身份实体和事实资料。资料分为用户声明、平台验证、公开来源三种证据级别。姓名、别名、医院、科室、职称、执业范围和擅长领域都应可追溯来源。

### 4.3 Semantic 模块

负责用户问题，不再把问题仅视为字符串。每条问题包含意图类型、是否带品牌、地区、目标人群、来源、版本和启停状态。

### 4.4 Monitoring 模块

负责创建 Run、拆分 Task、调用 Provider、记录 Observation。任何平台错误都必须成为错误状态，不得伪装成未提及。

### 4.5 Analysis 模块

基于原始回答识别实体提及、推荐关系、排名、情感、引用 URL、来源归属和竞品。分析结果保存分析器版本与证据片段，允许重放分析而不重新调用平台。

### 4.6 Content 模块

将监测缺口转化为内容机会，再形成草稿。内容必须绑定目标问题、依据资料、参考来源、风险等级和审核状态。

### 4.7 Distribution 模块

负责外部工具任务、发布记录、目标平台、URL 验证和发布状态。发布 URL 是后续归因的重要键，不能只维护文章计数。

### 4.8 Audit/Admin 模块

负责平台配置、模型配置、配额、用户禁用、合规规则、审计日志与失败任务处理。此模块只对平台管理员开放。

## 5. 三层监测体系

### 5.1 模型认知基准

普通聊天 API，不联网。用于判断模型静态认知和回答倾向，产品页面明确标记为“模型回答测试”。

### 5.2 联网搜索监测

调用能返回真实来源的搜索/问答能力。用于计算来源引用率、来源域名、竞品引用和内容机会，是商业核心指标。

### 5.3 消费者前台抽检

人工或低频合规采样真实产品前台，用于验证 API 结果代表性。抽检结果单独保存，不能与 API 自动监测混算。

## 6. 关键产品原则

### 6.1 数据诚实

- 不把接口失败解释为医生不可见；
- 不把医院出现解释为医生出现；
- 不把提及解释为推荐；
- 不把推荐解释为来源引用；
- 不把无序文本解释为第一名；
- 不把一次随机回答解释为长期趋势；
- 所有百分比展示样本数、成功覆盖率和统计周期。

### 6.2 证据优先

每个分析结论必须能展开查看：原始回答、命中的医生实体、证据片段、引用 URL、平台、模型、时间和分析器版本。

### 6.3 合规优先

医疗内容默认是草稿。系统必须阻止包含未验证资历、绝对化承诺、虚假效果、价格占位符或敏感病例的内容进入可发布状态。

### 6.4 可回退

新旧数据采用并行读取或双写过渡，不一次性删除历史表。所有迁移有备份、校验、回滚脚本和停机条件。

## 7. 旧模块处置

| 旧模块 | 当前处置 | V2 去向 |
|---|---|---|
| Question/MonitorRecord | 冻结写入，保留读取 | 迁移可识别记录，其余归档 |
| Content | 冻结新建 | 与 ArticleDraft 合并为 ContentItem |
| Knowledge/RAG | 从医生导航移除 | 评估后改为 Workspace 证据库或归档 |
| Competitor | 冻结旧全局数据 | 重建为医生监测结果中的实体与 Share of Voice |
| Platform 表 | 不继续扩建 | 合并到 Provider 配置与能力矩阵 |
| Subscription | 不作为真实收费依据 | 后续重建 Entitlement/Quota |
| Go CLI | 标记实验性 | 修复认证后仅保留管理员诊断能力，或归档 |

隔离是后端路由、权限和写入能力上的隔离，不是只从菜单隐藏。

## 8. 成功标准

### 8.1 产品成功

- 用户能解释每个指标代表什么；
- 用户能从缺失问题直接形成内容任务；
- 用户能看到内容发布前后的来源变化；
- 不再出现“AEO 已成功”但没有任何来源证据的情况。

### 8.2 数据成功

- 所有业务行都有 Workspace 归属；
- 所有采集请求都有明确成功或失败状态；
- 同一批次可以完整重放和审计；
- 删除、禁用和迁移不会产生孤儿记录。

### 8.3 工程成功

- 后端核心模块单元测试覆盖关键分支；
- API 契约自动生成前端类型；
- CI 完成格式、类型、测试、迁移和构建检查；
- 采集任务不阻塞 API；
- 任何上线批次都能在规定时间内回滚。

## 9. 实施阶段概览

1. 阶段 A：决策文档和影子实验，不改正式表。
2. 阶段 B：修复明确故障，建立测试与配置基线。
3. 阶段 C：Workspace、会话和审计安全底座。
4. 阶段 D：新监测模型与 Worker，旧链路保持只读。
5. 阶段 E：新数据中心与指标切换。
6. 阶段 F：内容合并、医疗审核和发布闭环。
7. 阶段 G：历史迁移、旧模块归档和正式商业化验收。

每阶段必须独立验收，不允许把 C 到 G 合并为一次大改。
