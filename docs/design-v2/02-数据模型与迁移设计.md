# 数据模型与迁移设计

## 1. 设计目标

新数据模型必须解决：跨用户数据泄漏、MonitorRecord 错误外键、采集批次不可追踪、失败与未提及混淆、内容双轨、审核缺失和发布无法归因。

原则：显式所有权、真实外键、可重放、可审计、可迁移、不过度抽象。

## 2. 数据所有权

所有业务对象归属于 Workspace，不直接以当前登录用户作为唯一所有者。User 表示身份，Workspace 表示业务数据边界，WorkspaceMember 表示授权关系。

    User ──< WorkspaceMember >── Workspace
                                  ├─ DoctorProfile
                                  ├─ SemanticQuestion
                                  ├─ MonitorRun
                                  ├─ ContentItem
                                  ├─ Distribution
                                  └─ AuditLog

初期一个用户自动创建一个个人 Workspace，体验不增加复杂度。

## 3. 身份与权限表

### 3.1 geo_user

保留现有表，新增：

- provider：iam；
- provider_subject：IAM sub，不可变；
- display_name；
- email；
- last_login_at；
- disabled_at；
- token_version，服务端撤销会话使用。

唯一约束：provider + provider_subject。username 只用于显示或兼容，不再作为 SSO 身份键。

### 3.2 geo_workspace

- id；
- name；
- type：personal、clinic、hospital；
- status：active、suspended、archived；
- timezone，默认 Asia/Shanghai；
- locale，默认 zh-CN；
- created_by；
- created_at、updated_at。

### 3.3 geo_workspace_member

- workspace_id；
- user_id；
- role：owner、editor、reviewer、viewer；
- status：active、invited、disabled；
- joined_at。

唯一约束：workspace_id + user_id。

角色建议：owner 管理成员与全部数据；editor 管理资料、语义和草稿；reviewer 审核内容；viewer 只读。平台 admin 不通过 Workspace role 表达，使用单独的平台角色。

## 4. 医生和证据

### 4.1 geo_doctor_profile

现有一用户一资料改为归属 Workspace：

- workspace_id；
- name；
- aliases，建议拆表；
- hospital、department、title；
- city、region_code；
- specialties；
- biography；
- verification_status；
- profile_version；
- created_by、updated_by；
- created_at、updated_at。

若确定一个 Workspace 只管理一个医生，可以先加 workspace_id 唯一约束；医院场景启用前再取消，不把 user_id 设为永久唯一。

### 4.2 geo_doctor_alias

- doctor_id；
- alias；
- alias_type：name、english_name、common_name、hospital_name_combo；
- verified；
- active。

医院名不能作为独立医生别名。

### 4.3 geo_evidence_source

- workspace_id；
- doctor_id；
- field_name；
- source_url；
- source_title；
- source_type：hospital、license、academic、owned、media、manual；
- verification_status；
- verified_by、verified_at；
- content_hash；
- last_checked_at。

它既支撑资料真实性，也支撑内容生成的事实来源。

## 5. 问题模型

### 5.1 geo_semantic_question

替代或演进现有 Semantic：

- workspace_id；
- doctor_id；
- question_text；
- normalized_text；
- intent_type；
- branded；
- region_code；
- locale；
- persona；
- source_type；
- topic_cluster；
- version；
- parent_question_id，用于版本或 fan-out 来源；
- status：draft、active、paused、archived、needs_review；
- created_by、created_at、updated_at。

不要继续使用 is_paid 表示授权。套餐和配额由 Entitlement 管理。

## 6. 监测模型

### 6.1 geo_monitor_run

一次用户操作、定时计划或基线实验创建一个 Run：

- id，建议 UUID；
- workspace_id；
- run_type：manual、scheduled、baseline、consumer_audit、reanalysis；
- mode：chat、grounded_search、consumer_audit；
- status：queued、running、partially_succeeded、succeeded、failed、cancelled；
- question_count；
- planned_observation_count；
- succeeded_count、failed_count、refused_count；
- requested_by；
- methodology_version；
- started_at、finished_at、created_at；
- estimated_cost、actual_cost；
- error_summary。

幂等键可由 workspace_id + client_request_id 构成，防止用户重复点击创建重复任务。

### 6.2 geo_monitor_observation

每次模型回答一行：

- run_id；
- workspace_id；
- question_id；
- question_version；
- provider；
- model；
- mode；
- region_code、locale、persona；
- prompt_template_id、prompt_hash；
- sample_index；
- status；
- raw_answer；
- raw_sources_json；
- provider_request_id；
- latency_ms；
- input_tokens、output_tokens、cost；
- error_code、error_message_safe；
- attempted_at、completed_at。

唯一约束：run_id + question_id + provider + model + sample_index。

### 6.3 geo_request_attempt

可选但推荐，用于记录重试：observation_id、attempt_no、status_code、error_code、latency_ms、started_at、finished_at。不得保存密钥或包含敏感信息的完整请求头。

### 6.4 geo_monitor_analysis

- observation_id，唯一；
- analyzer_version；
- target_mentioned；
- mention_evidence；
- recommendation；
- recommendation_evidence；
- rank，可空；
- sentiment；
- sole_recommendation；
- confidence；
- review_status；
- reviewed_by、reviewed_at；
- analyzed_at。

分析与原始 Observation 分离，允许升级算法后重算，不重复付费采集。

### 6.5 geo_citation

- analysis_id；
- raw_url；
- canonical_url；
- domain；
- title；
- position；
- source_owner_type：owned、hospital、earned、competitor、unrelated、unknown；
- related_to_target；
- supports_claim；
- http_status；
- checked_at。

### 6.6 geo_detected_entity

- analysis_id；
- entity_type：doctor、hospital、organization、treatment、disease；
- normalized_name；
- raw_text；
- role：target、competitor、source_author、other；
- recommendation；
- rank；
- sentiment；
- evidence_text。

竞品不再主要依赖用户手工维护的全局 Competitor 表，而从真实回答中识别；用户可将实体确认、合并或忽略。

## 7. 内容模型

### 7.1 geo_content_item

合并 ArticleDraft 与旧 Content 的目标模型：

- workspace_id；
- doctor_id；
- content_type：education、promotion；
- format：article、short_post、video_script、faq、profile；
- title、summary、body；
- status：draft、fact_check、medical_review、compliance_review、approved、published、rejected、archived；
- risk_level：low、medium、high；
- target_question_id；
- opportunity_id；
- version；
- generated_by；
- created_by、updated_by；
- approved_by、approved_at；
- created_at、updated_at。

不再维护容易漂移的 article_count。统计通过查询或可靠事件投影生成。

### 7.2 geo_content_evidence

- content_id；
- evidence_source_id 或 external_url；
- claim_text；
- source_excerpt；
- verification_status；
- verified_by。

### 7.3 geo_content_review

- content_id；
- content_version；
- review_type：fact、medical、compliance；
- result：approved、changes_requested、rejected；
- comments；
- reviewer_id；
- created_at。

审核结果绑定版本，内容修改后旧批准自动失效。

### 7.4 geo_content_opportunity

- workspace_id；
- doctor_id；
- question_id；
- opportunity_type：missing_mention、missing_citation、competitor_gap、outdated_source、inconsistent_entity；
- priority_score；
- evidence_json；
- status：open、planned、done、dismissed；
- created_at、resolved_at。

## 8. 发布与归因

### 8.1 geo_tool_task

保存外部图文/视频工具任务：workspace_id、content_id、tool_code、external_task_id、idempotency_key、status、request_payload_safe、result_url、error_code、created_at、updated_at。

### 8.2 geo_distribution

演进现有 ArticleDistribution：

- workspace_id；
- content_id；
- channel；
- external_content_id；
- published_url；
- canonical_url；
- status：planned、processing、published、failed、removed；
- publish_mode：api、webhook、manual；
- published_at；
- verified_at；
- created_by。

唯一约束建议为 workspace_id + channel + external_content_id；无 external_content_id 时使用 canonical_url 的条件唯一策略。

### 8.3 geo_attribution_event

记录发布后首次被抓取、首次被引用、引用次数变化等事件。归因只能表达时间与证据关联，不默认宣称单一内容导致指标变化。

## 9. 审计、配额和通知

### 9.1 geo_audit_log

记录 actor、workspace、action、resource_type、resource_id、before_json、after_json、request_id、ip、created_at。敏感字段脱敏，不记录 Token 和密钥。

必须审计：资料修改、成员权限、语义增删、采集触发、内容审核、发布、平台配置和导出。

### 9.2 geo_entitlement 与 geo_usage_ledger

Entitlement 定义套餐能力和周期配额；UsageLedger 记录每次消耗。接口先检查授权，再创建任务。现有 add-paid 不再自行设置 is_paid。

### 9.3 geo_notification

用于任务完成、失败、指标异常、待审核和发布失败。前端通知铃必须读取真实数据，否则删除占位 UI。

## 10. 数据库约束

- 所有业务表 workspace_id 非空并有索引；
- 所有外键明确 ON DELETE 行为；
- 枚举在应用层与数据库约束保持一致；
- 时间统一存 UTC，展示按 Workspace timezone；
- 重要更新使用 version 做乐观锁；
- published_url 只允许 http/https；
- JSON 字段保存扩展信息，不能替代关键可查询列；
- PostgreSQL 为目标生产数据库；SQLite 仅限本地开发或测试。

## 11. Alembic 迁移步骤

### 11.1 准备

1. 引入 Alembic；
2. 建立当前 13 张表的基线 revision；
3. 在 SQLite 副本和空 PostgreSQL 分别演练；
4. 导出旧表行数、外键异常和孤儿数据报告；
5. 对生产数据库创建可恢复备份。

### 11.2 扩展阶段

只新增 Workspace、新监测表、审计表和必要字段，不删除旧列。为每个现有 User 创建个人 Workspace，并建立 owner 成员关系。

### 11.3 回填阶段

- DoctorProfile、Semantic、ArticleDraft、Distribution 根据 user_id 回填 workspace_id；
- 旧 Question、Content、Knowledge、Competitor 无法可靠识别所有者，禁止自动平均分配；
- 能通过创建人、脚本记录或业务确认识别的才迁移；
- 不可识别数据进入 legacy_archive 并仅管理员可见；
- 旧 MonitorRecord 中 detect_type=doctor 且 semantic_id 可验证的记录可转换为历史 Run/Observation；
- question_id 与 semantic_id 冲突或平台错误文本需标记 migration_warning。

### 11.4 双读/双写阶段

推荐先让新采集只写新表，新 Dashboard 通过功能开关读取新表；旧 Dashboard 保持读取旧表。内容迁移可短期双写，但必须有对账任务。不要长期双写。

### 11.5 切换阶段

达到测试门槛后：默认打开 V2 Dashboard；关闭旧模块写接口；保留旧数据只读导出；观察至少一个完整监测周期。

### 11.6 收缩阶段

只有完成备份、对账、使用日志确认和业务签字后，才删除旧表/字段。删除必须单独 revision，不与功能上线同批执行。

## 12. 回滚策略

- 每个 revision 提供 downgrade 或明确不可逆说明；
- 上线前保留数据库快照；
- V2 页面用 Feature Flag 切换；
- 新写入失败时不回写伪造的旧指标；
- 回滚应用不等于回滚数据，需分别演练；
- 一旦新表已产生用户内容，禁止通过删除表完成回滚。

## 13. 迁移验收

- [ ] 每个用户有且仅有一个默认个人 Workspace；
- [ ] Doctor、Semantic、Article、Distribution 回填数量与源表匹配；
- [ ] 无法确定归属的旧数据没有泄漏给普通用户；
- [ ] 新 Observation 不再复用 Question 外键；
- [ ] 失败记录可查询但不参与可见度；
- [ ] 新旧指标对账差异有解释报告；
- [ ] PostgreSQL 从空库升级成功；
- [ ] SQLite 副本迁移成功或明确仅支持导出迁移；
- [ ] 回滚演练通过。
